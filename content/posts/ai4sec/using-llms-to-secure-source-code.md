:::important[Problem]
LLM 已经能够并行阅读大型代码库并提出大量漏洞候选，但候选数量增加并不等于代码更安全。如果缺少明确的威胁模型、可复现环境、独立验证、去重定级和修复回归，安全团队得到的只会是一份越来越长的告警列表。

**核心问题是：如何把 LLM 的代码理解能力接入一条可验证、可排序、可修复、可持续运行的安全工程闭环？**
:::

## 1. 整体结构：Find-and-Fix Loop

完整流程拆成六步：

| 阶段 | 中文理解 | 主要目标 | 主要产物 |
| --- | --- | --- | --- |
| 1. Threat Model | 威胁建模 | 先定义什么才算漏洞 | `THREAT_MODEL.md` |
| 2. Sandbox | 沙箱 | 隔离 Agent，并提供可运行的验证环境 | 固定版本的测试环境 |
| 3. Discovery | 漏洞发现 | 尽量召回潜在漏洞 | 结构化候选报告与 PoC |
| 4. Verification | 独立验证 | 排除不可利用或被防护的候选 | 可复现证据与验证结论 |
| 5. Triage | 安全分诊 | 去重、定级并确定修复顺序 | 短且有优先级的漏洞列表 |
| 6. Patching | 补丁修复 | 修复根因、验证补丁并查找变体 | 最小补丁、测试和复扫结果 |

![The defender's loop：威胁建模、沙箱、发现、验证、分诊与修复](./image/find-and-fix-loop.png)

_图 1：Defender's Loop。威胁模型和沙箱是一次性投入，Discovery → Verification → Triage → Patching 则需要周期性运行。_

前两个阶段属于基础设施建设，代码库或部署方式发生重要变化时再更新；后四个阶段构成持续循环，应在代码显著变化或固定周期内重复执行。

模型具有随机性，同一个代码库多次扫描仍可能发现新的长尾问题。因此，第一次扫描不应只运行一次，而应根据新增漏洞数量和系统风险决定何时停止；之后继续做周期扫描和变更触发扫描。

## 2. Threat Model：先定义什么算漏洞

Threat Model（威胁模型）描述系统资产、入口、攻击者能力、信任边界以及团队关心或不关心的漏洞类型。

常见误报并不一定来自模型不懂代码，而是模型错误理解了信任边界：

- 把受信任配置误认为攻击者可控，产生误报；
- 把公网服务误认为内部服务，遗漏真实攻击面；
- 看到危险函数，却不知道上游认证、类型约束或 WAF 已经阻断利用；
- 只根据漏洞类别判断严重性，没有结合真实部署条件。

### 2.1 从现有材料生成初稿

应向模型提供一名新安全工程师入职时需要阅读的信息：

- 架构文档、Wiki 和关键入口；
- Git 历史和安全修复提交；
- 历史 CVE、漏洞报告和 Bug Bounty 记录；
- 依赖项目的安全策略；
- 系统资产、部署环境和信任假设。

模型先生成包含系统上下文、资产、入口和信任边界的草稿，再对历史漏洞聚类，提取项目特有的 bug shape（漏洞形态）。相比泛泛地要求“找漏洞”，沿着过去真实发生过的漏洞模式检查补丁是否完整、相同问题是否存在于其他位置，目标更明确。

### 2.2 让系统负责人补充隐含知识

代码和文档无法表达所有设计决策，因此需要让模型采访熟悉系统的人，围绕四个问题完善草稿：

1. 我们正在构建什么？
2. 可能发生什么错误？
3. 我们准备如何应对？
4. 当前措施是否足够？

最终将结果保存在代码仓库的 `THREAT_MODEL.md` 中。发现阶段用它确定扫描范围，分诊阶段用它校准严重性。

## 3. Sandbox：隔离执行并证明可利用性

Sandbox（沙箱）同时承担两个任务：

1. 防止安全 Agent 在扫描过程中影响真实系统；
2. 为漏洞候选提供编译、运行测试和触发 PoC 的环境。

隔离级别需要与风险匹配：

- 只读代码发现可以运行在容器中；
- 执行目标程序和 PoC 时优先使用 microVM（轻量虚拟机）或完整虚拟机；
- 默认关闭出口网络，只通过本地代理访问模型 API；
- 不向 Agent 暴露 `~/.aws`、`~/.ssh`、`.env` 等凭据；
- 固定镜像标签、Commit SHA、依赖版本和构建命令；
- 每次扫描从相同的干净快照启动。

环境必须尽量接近生产：缺少消息队列或数据库可能让真实路径不可达；忽略生产中的认证网关、WAF 等补偿控制，又会把实际不可利用的问题判断为漏洞。

PoC（Proof of Concept，概念验证）可以是触发脚本、崩溃输入或失败测试。模型只有在真实环境中运行 PoC，才能检查代码路径是否可达、攻击输入是否真的到达危险点，以及是否存在遗漏的防护。

## 4. Discovery：优化召回率，不要过早自我否定

Discovery（漏洞发现）的目标是提高 Recall（召回率），即尽可能找出真实漏洞，即使暂时保留一些不确定候选。

### 4.1 提供丰富上下文，但保持 Prompt 简洁

前沿模型在发现阶段反而受益于更简单的提示：过长的漏洞检查清单会限制探索范围，减少新颖漏洞。

更合适的方式是：

- 告诉模型为什么扫描、目标系统是什么、什么发现有价值；
- 如果关注某类漏洞，说明其机制和常见位置；
- 规定结构化输出字段，如证据、数据流、影响和严重性；
- 允许模型在证据不足时提前退出，而不是强行生成漏洞。

### 4.2 给 Agent 足够的代码和安全工具

Agent 至少需要搜索、读取和追踪代码的能力，还可以结合：

- SAST（静态应用安全测试）扫描器；
- Fuzzer（模糊测试器）；
- HTTP 请求与响应检查；
- 流量日志和运行状态；
- 为当前任务临时编写的分析脚本。

如果存在可运行沙箱，发现 Agent 应尽量为候选生成 PoC；无法复现的候选仍可保留，但必须标记为 `unproven`，避免把假设写成已经证实的漏洞。

### 4.3 按攻击面切分并行任务

先由一个 Agent 按组件、入口或攻击面划分搜索空间，再让多个发现 Agent 分别处理不同区域，最后进行一次系统级跨组件分析。

简单增加大量相同 Prompt 的 Agent ~~就能线性增加有效漏洞~~。它们容易集中发现相同的浅层问题，产生大量重复报告。并行化需要搜索空间分工，而不只是横向复制。

## 5. Verification：用独立 Agent 主动证伪

Verification（验证）优化 Precision（精确率）：它不负责继续扩大候选集合，而是排除不可利用、不可达或已被其他控制缓解的发现。

发现 Agent 和验证 Agent 应相互独立：

- 使用新的容器和对话上下文；
- 不共享发现 Agent 的推理过程；
- 只提供代码库、候选报告和 PoC；
- 要求验证 Agent 默认把候选视为误报，主动寻找反证；
- 检查上游校验、认证、类型约束、不可达代码和补偿控制。

如果一次验证仍留下过多误报，可以运行多个独立验证 Agent，通过多数投票或额外 Judge（裁决 Agent）综合判断。

Anthropic 总结其合作团队的经验：对抗式验证大约将不可利用发现减半；如果再要求验证 Agent 生成并执行 PoC，误报率可以接近零。不过这些数字来自不同团队实践，并不是在统一数据集、统一模型和统一判定标准上的严格对照实验。

此外，还要注意一个不对称关系：

```text
PoC 成功  → 能有力证明当前环境下可利用
PoC 失败  ↛ 能证明漏洞不存在
```

PoC 失败可能来自环境不完整、触发条件未知或验证脚本错误，因此只能降低置信度，不能自动判为误报。

## 6. Triage：按根因去重，按利用条件定级

Triage（安全分诊）回答的不是“漏洞是否存在”，而是“哪些漏洞应该先修”。

### 6.1 根据根因去重

扫描器可能在多个调用点报告同一个缺失校验，也可能把一个根因的不同后果拆成多条漏洞。可以先做低成本确定性合并，例如同文件、同类别且行号接近，再让模型判断剩余候选。

| 应视为重复 | 应视为独立漏洞 |
| --- | --- |
| 同一根因的不同表述 | 同一文件中的不同漏洞类别 |
| 同一漏洞在多个调用点触发 | 不同变量到达不同 Sink |
| 缺失全局认证被每个接口分别报告 | 同一 Helper 中互不依赖的两个缺陷 |
| 同一路径中的原因和后果 | 需要分别修复的两个独立入口 |

如果每条候选都有 PoC 和补丁，还可以用“某个补丁是否同时阻断其他 PoC”辅助判断它们是否共享根因。

### 6.2 严重性必须由证据逐项推导

在给出等级前需要逐项回答：

- **Reachability**：攻击者能否从真实入口到达该代码？
- **Attacker control**：不可信输入是否完整到达危险点？
- **Preconditions**：是否依赖非默认配置、Feature Flag 或狭窄时间窗口？
- **Authentication**：未认证用户、普通用户还是管理员才能触发？
- **Read vs. write**：只能读取数据，还是可以修改状态？
- **Blast radius**：影响一个用户、租户、整个平台还是内核？

应先写出每一项证据，再给出严重性，避免看到“SQL 注入”就直接锚定为 Critical。相同漏洞类别在公网未认证入口和管理员本地配置中的风险完全不同。

## 7. Patching：修复根因并关闭循环

补丁阶段不只是生成代码 Diff，还需要证明漏洞已经消失且功能没有被破坏。

补丁阶段采用以下顺序：

1. 先添加一个能够复现漏洞、在旧代码上失败的测试；
2. 修复漏洞根因，而不只封堵当前调用点；
3. 确认复现测试在新代码上通过；
4. 运行原有测试，检查功能回归；
5. 搜索相同模式和相同漏洞类别的变体；
6. 让新的发现 Agent 从攻击者视角重新检查补丁；
7. 将验证结果和新的信任边界反馈到威胁模型。

补丁应尽量小，避免顺手重构、格式化或清理无关代码。过度严格的自动修复虽然可能阻断 PoC，却也可能破坏正常输入或服务依赖。

补丁验证可以形成由低成本到高成本的阶梯：

| 顺序 | 检查 | 发现的问题 |
| --- | --- | --- |
| 1 | Build + 新测试 | 编译失败或补丁基本错误 |
| 2 | 重放原始 PoC | 修复无效 |
| 3 | 完整回归测试 | 正常功能被破坏 |
| 4 | 新 Agent 重新攻击 | 修复不完整或仍有绕过 |

即使模型完成了这些检查，最终补丁仍需要由人类负责。模型可能不了解即将合入的代码、团队约定、真实依赖和业务兼容性。

## 8. 如何在真实项目中落地

可以从一个服务或组件开始，而不是立即扫描整个组织：

```text
整理代码与文档
  → 生成并人工确认 THREAT_MODEL.md
  → 构建固定依赖、无凭据、限制网络的沙箱
  → 按攻击面切分并行扫描
  → 独立 Agent 验证并复现 PoC
  → 按根因去重、按条件定级
  → 生成最小补丁并逐级验证
  → 更新威胁模型并定期复扫
```

Anthropic 提供了配套的 `defending-code-reference-harness`，包含交互式工作流、自治扫描 Demo，以及 threat-model、vuln-scan、triage 和 patch 等阶段技能。

第一次扫描通常会产生最多候选，因此项目计划不能只给 Discovery 分配预算，还应提前准备验证环境、安全工程师审查时间和开发团队修复容量。
